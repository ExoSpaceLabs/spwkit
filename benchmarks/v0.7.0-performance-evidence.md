# SpWKit v0.7.0 performance acceptance evidence

## Scope

This record captures the release-performance review for the v0.7 runtime candidate against immutable `v0.6.1`.

The primary release baseline is:

- `v0.6.1`: `03869c0b3bc9e895e0fe61a36f24cff2ace7d527`

The runtime candidate measured after the LOOPBACK duplicate-validation cleanup is:

- candidate: `23eceeb0389e02d66febf5a0f027cc3e9153b14a`

The candidate commit contains the same v0.7 runtime-contract/backend-equivalence implementation as `develop` plus the narrow LOOPBACK hot-path cleanup from PR #226. Documentation-only commits after this measurement do not change the measured runtime source.

## Controlled repeated campaign

GitHub Actions run `34509009730` executed three complete baseline/candidate pairs sequentially in one job on the same hosted machine and pinned logical CPU.

Recorded environment and policy:

- Ubuntu 24.04 / Linux `6.17.0-1022-azure`;
- AMD EPYC 7763 64-Core Processor;
- GCC 13.3.0;
- x86 `RDTSCP` architectural counter;
- measurement pinned to logical CPU 0;
- 256 warmup iterations;
- 1024 measured iterations per payload/path;
- payloads `0 1 8 64 256 1024 4096` bytes;
- failed fixture attempts are discarded as complete pairs rather than mixed with accepted evidence.

All three accepted pairs completed and were internally comparable.

### Result disposition

- **LOOPBACK TX/RX:** no recurring release regression after PR #226. Most medians are exactly equal to v0.6.1. The remaining 4096-byte TX movement changes direction between runs and is treated as counter/scheduler variation.
- **SIMULATOR TX/RX:** no attributable broad regression. Small one-counter-quantum observations are not stable across payloads/runs and the relevant copied receive body is unchanged from v0.6.1.
- **DRIVER copied TX/RX:** effectively flat. Copied RX is normally zero native-relative delta; copied TX is normally 0-1 tick of native-relative overhead.
- **DRIVER zero-copy TX:** effectively flat. Acquire and submit ownership-path medians are normally identical to v0.6.1.
- **VSPW-TP/UDP:** release deltas remain small relative to transport cost, generally fractions of a percent to approximately 2%, with no recurring v0.7 regression requiring optimization.
- **Lifecycle:** effectively flat. Small 1-tick or single-counter-quantum changes remain below the release triage threshold and do not indicate a changed lifecycle bottleneck.
- **DEVICE/VSPD:** hosted measurements remain strongly scheduler/kernel/daemon sensitive and swing by hundreds to tens of thousands of ticks in both directions. The DEVICE implementation itself did not change between v0.6.1 and the v0.7 candidate, so these hosted deltas are not used as evidence for speculative runtime optimization.

## Zero-copy RX release investigation

The repeated release campaign initially showed `driver.zero-copy.rx.release` moving from approximately 98 to 122 architectural counter ticks, a +24-tick step for every payload in all three pairs. Because that result was perfectly repeatable in the original campaign, it was investigated rather than dismissed.

### Per-call origin probe

Run `34532768670` compared three local variants built from the exact candidate runtime commit:

1. **current** — the v0.7 ownership-epoch validation as implemented;
2. **direct** — a semantics-preserving rewrite that checks the port-owned epoch pointer directly before comparing the epoch value;
3. **bypass** — a measurement-only control that removes the new ownership check from RX release. This variant is not release code and must never be merged.

Each variant was measured five times with 4096 samples per run on one pinned CPU. The standalone counter-floor median was approximately 52 ticks.

| Variant | Release medians | Median of medians | Disassembled release instructions |
|---|---|---:|---:|
| current | `78, 78, 78, 78, 78` | 78 ticks | 54 |
| direct | `78, 78, 78, 78, 78` | 78 ticks | 50 |
| bypass | `78, 78, 78, 78, 78` | 78 ticks | 38 |

Removing sixteen instructions from the measured function did not change the per-call median. The earlier +24-tick plateau therefore cannot be interpreted as a literal 24-tick ownership-validation cost; the individual call is too close to the `RDTSCP` measurement floor/quantization for that inference.

### Batched origin probe

Run `34532970619` then amortized the counter-read cost by timing two million deterministic DRIVER acquire+release pairs inside one outer counter interval. Nine interleaved runs of each source variant were performed on one pinned CPU.

| Variant | Median ticks / acquire+release pair | Observed range |
|---|---:|---:|
| current | 77.332388 | 76.337161 .. 80.104354 |
| direct | 77.990654 | 77.493831 .. 82.600231 |
| bypass | 75.270051 | 74.443593 .. 75.739974 |

The current-minus-bypass delta is **+2.062337 ticks per acquire+release pair**. Because the only source difference between those two variants is the RX-release ownership guard, this is the best measured estimate of its fixed hot-path cost in this environment.

The attempted semantics-preserving direct rewrite was **+0.658266 ticks per pair slower** than the current implementation, so it provides no optimization justification.

### Acceptance decision

The approximately two-tick fixed cost is accepted as the quantified cost of the v0.7 ownership contract. The check protects two required semantics introduced by the runtime-contract hardening:

- a zero-copy handle may only be returned through the `spw_port_t` that owns it;
- handles from a pre-reset ownership epoch are stale and must be rejected.

The investigation found no demonstrated equivalent implementation that is faster than the current check. Removing the guard would weaken the v0.7 correctness contract for an approximately two-tick saving and is therefore rejected.

The original +24-tick per-call observation is retained as useful evidence about measurement granularity, not as the accepted implementation cost.

## Release-performance conclusion

The v0.7 candidate has no unexplained reproducible software regression that warrants additional runtime optimization before release. The one attributable new fixed cost, zero-copy RX ownership validation, is approximately two architectural counter ticks per acquire+release pair in the batched probe and is required by the new reset-safe/cross-port ownership semantics.

PR #226's LOOPBACK cleanup is justified because it removes validation already performed by the public core while preserving backend-specific state, packet-size and resource checks; repeated profiling shows the LOOPBACK path back within normal v0.6.1 variation.

Final release acceptance still requires the post-merge candidate to pass the complete functional/platform/profiling CI suite and the final release-candidate evidence to be frozen before tagging `v0.7.0`.
