# SpWKit v0.6 hardware integration boundary

v0.6 moves SpWKit from software-only transport backends toward a reusable hardware-driver integration boundary without claiming an FPGA implementation or physical SpaceWire interoperability that does not exist yet.

## Objective

Applications keep using the normal `spw_port_*` API while the selected backend may be implemented by a simulator, UDP/VSPW-TP, Linux VSPD, or a platform/vendor SpaceWire driver.

```text
Application
    |
    v
spw_port_* public C API
    |
    +-- simulator / UDP / VSPD
    |
    +-- driver backend
            |
            +-- host reference driver (CI)
            +-- RTOS/bare-metal driver
            +-- future MMIO/DMA FPGA driver
                    |
                    +-- future SpaceWire HDL/IP core
```

## v0.6 scope

1. Reconcile public documentation with the released v0.5.0 boundary.
2. Define a portable driver callback/configuration contract behind a normal SpWKit backend ID.
3. Preserve packet boundaries, EOP/EEP, time codes, link state/control, readiness, statistics and timeout/error semantics through that driver boundary.
4. Map driver-owned DMA-capable buffers onto the existing SpWKit zero-copy ownership API rather than inventing a second application-facing packet API.
5. Provide a deterministic host reference driver so the complete contract can execute in ordinary CI without hardware.
6. Keep the driver contract usable with heap disabled and without POSIX, sockets, threads or operating-system file descriptors.
7. Document the later HDL boundary explicitly: register map, descriptor format, interrupt model, DMA coherency and electrical/HIL behavior are not guessed in v0.6.

## Stop condition

v0.6 software work is complete when a vendor/FPGA driver can be written against a stable documented contract and validated with the reusable backend tests. Work then stops before implementing a real SpaceWire HDL core or asserting physical interoperability. Those require a separately defined FPGA/IP specification and hardware evidence.
